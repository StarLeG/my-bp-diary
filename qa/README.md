# Нагрузочное тестирование — «Дневник гипертоника»

Цель: доказать, что система стабильно работает при **20 одновременных активных пользователях** и базе на **5000 измерений** (плюс лекарства, логи приёма, напоминания и врачи). При этом не должно быть потери данных, ответов 5xx/403/429 и дублей.

Нормативное описание — [SPEC.md §22](../doc/SPEC.md), исходная постановка — [TEST TZ](../doc/TEST%20TZ.md), протокол решений — [LOAD-TESTS-QUESTIONS](../doc/LOAD-TESTS-QUESTIONS.md). При расхождении действует SPEC.

> E2E-тесты QA-стенда (`test_telegram_e2e.py`, `test_web_e2e.py`: Telethon и Playwright) живут в этой же папке, но к нагрузке не относятся. Как их запускать, описано в `qa/docker-compose.qa.yml` и `qa/conftest.py`.

## Безопасность

- **Только тестовый стенд.** Сиды и тесты работают только с БД, в имени файла которой есть `test-stand`. Это `data/test-stand.sqlite3` (переменная `LOAD_DB`) или `test-stand.sqlite3` во временной папке теста. С любой другой БД (прод `bot.sqlite3`, флешмоб `flashmob.sqlite3`) они отказываются работать, и обойти это нельзя.
- **Без реального Telegram API**: бот прогоняется через `Dispatcher` с подменённой сетевой сессией. Настоящие аккаунты участвуют только в ручном флешмобе.
- **Прод-код не меняется**: фейковые часы, сдвиг времени и мок-бот живут в фикстурах `qa/conftest.py`.
- **Пароли** нагрузочных пациентов и врачей берутся только из `LOAD_PASSWORD`. Сиды и Locust без этой переменной не запускаются. pytest при её отсутствии генерирует случайный пароль на сессию и держит его только в памяти.

## Профили

| Профиль | Как включить | Объём | Где БД |
|---|---|---|---|
| Дымовой | `uv run pytest qa/` (без флага) | 3 пациента, по 25 измерений, 3 врача, 3 пользователя × 5 операций | временный файл SQLite с PRAGMA прода |
| Полный | `LOAD_TEST=1` | 20 пациентов, 5000 измерений, 100 лекарств, 500 логов, 100 напоминаний, 20 врачей | временные копии шаблона + стенд `data/test-stand.sqlite3` |

In-memory SQLite не используется ни в одном профиле: в ней нет настоящих блокировок, и гонки не воспроизводятся. Каталог `qa/` в CI не входит, туда попадает только юнит-тест сидов `tests/test_qa_seed.py`.

## Сид

- **Расписание детерминированное и привязано к дате создания пациента** (`users.created_at`), а не к «сегодня». Поэтому повторный запуск в любой день даёт те же моменты и ничего не дублирует. Окно — 30 дней до даты создания, моментов в будущем нет. Чтобы окно снова стало «последними 30 днями», запустите сид с `--clean`.
- **Сидированные моменты — с секундой `:17`** (`qa.seed.SEED_SECOND`). Форма кабинета пишет время с точностью до минуты, поэтому регрессия отличает 5000 сидированных записей от добавленных нагрузкой.
- **Пароль хешируется один раз за запуск** (Argon2id, соль хранится в самом хеше). Пароль существующих аккаунтов при повторном сиде не меняется: для нового пароля нужен `--clean`.
- **`--clean` удаляет** пациентов с TG ID 990 001…990 999 (остальное каскадом) и врачей `*@load.test`. Job'ы их напоминаний сначала снимаются из таблицы `apscheduler_jobs`, если бот когда-либо работал на стенде. Администратор и любые другие данные остаются.
- **В pytest** шаблон стенда собирается один раз за сессию (`load_template`), каждый тест получает копию через Online Backup API SQLite (`load_db`).

## Подготовка

```bash
uv sync --group load                      # Locust, pytest-html, Playwright
uv run playwright install chromium        # для скриншотов (один раз)
```

**Машина для приёмки — без троттлинга.** Тайминговые пороги (p95 карточки врача, Locust) снимаются на сервере или на ПК со схемой питания «Высокая производительность» и без фоновой нагрузки. Ноутбук на «Сбалансированной» схеме через 1–2 с нагрузки замедляет процесс до ~3×, и p95 врача выходит за 2 с без всякой вины кода. `test_load_doctor` и `test_load_backup` пишут калибровку (`calibration_ms`, множитель `slowdown_vs_reference`) в JSON и в сообщение о падении: множитель ≈ 2–3 — машина, ≈ 1 — код.

Важно: `uv sync` без `--group load` удалит эти пакеты из `.venv`. Под Windows Locust без `PYTHONUTF8=1` пишет CSV в системной кодировке. Регрессия читает оба варианта, но UTF-8 удобнее.

## Запуск

```bash
# 1. Сид стенда (полный масштаб; --clean — пересоздать только нагрузочные данные)
LOAD_PASSWORD='<пароль стенда>' \
    uv run python qa/seed/seed_all.py --db data/test-stand.sqlite3

# 2. Дымовой прогон (секунды)
uv run pytest qa/ -v

# 3. Полный набор нагрузочных тестов
LOAD_TEST=1 uv run pytest qa/ -v -s --ignore=qa/locustfile.py

# 4. HTTP-нагрузка кабинета: сначала кабинет на стенде, затем Locust
DB_PATH=data/test-stand.sqlite3 uv run uvicorn web.cabinet.app:app --port 8000
LOAD_PASSWORD='<пароль стенда>' PYTHONUTF8=1 \
    uv run locust -f qa/locustfile.py --host=http://127.0.0.1:8000 \
    -u 20 -r 2 -t 5m --headless --csv=qa/reports/load/locust

# 5. Регрессия критериев приёмки
LOAD_TEST=1 uv run pytest qa/test_load_regression.py -v
```

## Критерии приёмки

Каждый нагрузочный тест проверяет свои критерии сам и в полном профиле пишет итог в `qa/reports/load/<тест>.json`. `test_load_regression.py` (только с `LOAD_TEST=1`) собирает эти JSON, Locust CSV и БД стенда:

- нет JSON какого-либо теста — FAIL «не запускался»;
- нет Locust CSV — проверки Locust пропускаются (SKIP).

| Метрика | Порог | Источник |
|---|---|---|
| HTTP 5xx, 403, 429 | 0 | Locust CSV |
| p95 `/` и `/?days=30` | < 2000 мс | Locust CSV |
| p95 CSV измерений и лекарств за 30 дней | < 3000 мс | Locust CSV |
| Дубли измерений за минуту | 0 | SQL (стенд) и JSON тестов |
| Дубли `medication_logs` по `(user_id, slot, локальная дата, medication_id)`, кроме `crisis` | 0 | SQL и JSON |
| Дубли отправленных напоминаний | 0 | JSON `test_load_reminders` |
| `integrity_check` после бэкапа | `ok` | JSON `test_load_backup` |
| Нагрузочные пациенты в `users` | 20 | SQL (стенд) |
| Сидированные измерения на месте | 5000 (новые от Locust допускаются) | SQL (стенд) |

## Артефакты и логи

- `qa/reports/load/<тест>.json` — итоги тестов. В начале полного прогона старые JSON удаляются (если в сессии есть хотя бы один `test_load_*`, кроме регрессии), Locust CSV остаётся.
- `qa/reports/load/qa-load.jsonl` — лог `qa.load` в виде JSON-строк (`op`, `user_id`, `duration_ms`, …), пересоздаётся в начале полного прогона. В консоль выводятся только сводки.
- `qa/reports/load/locust_*.csv` — статистика Locust.
- `qa/reports/screenshots/` — скриншоты.
- Дымовой прогон артефактов не пишет, чтобы не затирать результаты полного. Весь `qa/reports/` лежит вне git (`.gitignore`), выдержки отчётов — ниже.

## Найденные узкие места

Цифры сняты на машине разработчика (Windows, Python 3.14, SQLite WAL). На сервере они будут другими. 

| Где | Что видно | Что это значит |
|---|---|---|
| Сид стенда | полный профиль — 1,3 с, повторный запуск — 0,3 с, шаблон pytest — 1,4 с | для стенда не проблема |
| `test_load_burst`, массовая запись | 1000 конкурентных сохранений — 15,6 с (~64 записи/с), p95 одной операции — 14,8 с | сохранения проходят по одному: общий лок дедупа (§7.2) плюс коммит каждой записи. Лимит 60 с выдержан, ошибок и `database is locked` нет. При 20 живых пользователях (единицы записей в минуту) запаса на порядки больше |
| `test_load_burst`, остальные сценарии | двойные нажатия 1000 оп. — 2,7 с; правки 1000 — 4,8 с; «Принял всё ✓» 200 — 0,4 с; `/start` 400 — 1,0 с | в пределах нормы |
| `test_load_bot` | 20 пользователей: 22–26 с на «быстрой» машине, 51–55 с под троттлингом | время зависит от машины, критерий — 0 ошибок и все строки |
| Кабинет врача, PDF | ~90 мс на отчёт за 30 дней (~260 мс под троттлингом), 78% CPU флоу врача | синхронный PDF и Argon2id останавливали весь кабинет — p95 карточки 3,8 с; исправлено `fix(cabinet)` (`asyncio.to_thread`), стало 0,6–1,0 с |
| Бэкап, запись мимо лока | p95 64–95 мс, max 0,2–0,7 с; изредка до 5,5 с вне окна бэкапа | `VACUUM INTO` через WAL записи не мешает; выбросы — неравноправность busy-обработчика SQLite, проходят повтором |
| Машина разработчика | i5-12450HX: через 1–2 с непрерывной нагрузки любой процесс замедляется ~3× | управление питанием Windows, не код; все тайминги выше снимать на незатроттленной машине (вопрос V3) |

## Что делать при падении

| Что упало | Куда смотреть | Типовая причина |
|---|---|---|
| `test_artifact_passed[<тест>]` — «не запускался» | был ли `test_load_<тест>` в сессии и не SKIP ли он | регрессия запущена без полного прогона; скриншоты — без запущенного кабинета или `LOAD_PASSWORD` |
| Любой тест — `database is locked` | `failure_samples` в JSON, `qa-load.jsonl` | ожидание asyncio-лока с незакоммиченной записью SQLite (§7.2) — так нашлись T1, U1, U2 |
| `test_load_bot` — не все строки / ошибки | `errors`, `rows_added` в JSON; `qa-load.jsonl` по `user_id` | исключение в хендлере, дедуп минуты (время виртуальных часов), debounce |
| p95 (врач, Locust) выше порога | `p95_ms` и `calibration_ms.slowdown_vs_reference` в JSON, `locust_stats.csv`; время `test_load_bot` в том же прогоне | синхронная тяжёлая работа в event loop — или троттлинг машины (бот тоже вдвое медленнее обычного) |
| `test_load_backup` — p95 пробы ≥ 1 с | `slow_probes`, `probe_p95_s`, `calibration_ms.slowdown_vs_reference` | массовая деградация записи под бэкапом; одиночные выбросы max допустимы |
| `test_load_reminders` — дубли / недоставка | `duplicates`, `sent`, `timed_out` | атомарный захват `last_sent_date`, перепланировка job'ов |
| Регрессия БД стенда | сообщение с `user_id` | стенд пересеян без `--clean` другим масштабом или Locust не тем паролем |

## Живой флешмоб (ручной сценарий для 20 реальных аккаунтов)

Отдельная БД, нагрузочные данные сюда не попадают. Бот флешмоба запускается с токеном **тестового** бота:

```bash
DB_PATH=data/flashmob.sqlite3 uv run python -m bot
```

Чек-лист участника (все действуют параллельно, на созвоне или в общем чате, всё вместе укладывается в 10 минут):

1. Найти тестового бота и нажать `/start`.
2. Пройти онбординг: часовой пояс `Europe/Minsk`, цель 130/80.
3. Сделать 5 записей давления.
4. Добавить 2 лекарства.
5. Поставить любой слот напоминания на «сейчас + 2 мин», дождаться напоминания и ответить «Записать давление» или «Принял всё ✓». Кнопку «Через 30 мин» достаточно нажать и убедиться, что бот ответил.
6. Экспортировать CSV.

Проверка владельцем стенда (SQL на `data/flashmob.sqlite3`):

```sql
SELECT COUNT(*) FROM measurements;                                    -- ожидается 100
SELECT COUNT(*) FROM (SELECT DISTINCT user_id, name FROM medications); -- ожидается 40
```

## Перед релизом (авто-приёмка)

Долгие проверки критериев «Полный объём», «Деградация», «Длительная работа»,
«Возврат памяти», «Рост файлов и базы», «Остановка» (SPEC.md, §22 «Приёмка
перед релизом»; ответы — `doc/LOAD-CRITERIA-QUESTIONS.md`). На своей машине —
перед выпуском версии и после любой правки, касающейся хранения данных; в
обычную сдачу и в CI не входят.

```bash
# 1. Стенд полного масштаба + генератор ~50 000 вымышленных записей за 3 года
LOAD_PASSWORD='<пароль стенда>' \
    uv run python qa/seed/seed_all.py --db data/test-stand.sqlite3 --scale three-years

# 2. Все проверки (часовая soak — самая долгая) + регрессия по артефактам
make acceptance
```

**Ожидаемое время:** полный объём ~10 с (замеры — против реального сервера
`uvicorn --workers 2`), деградация ~1 мин (CSV — 200–300 вызовов), часовая
soak — 60 мин + 10 мин прогрева, возврат памяти ~2 мин (+60 с покоя),
рост < 1 мин, остановка ~10 с; итого чуть больше часа.

**При падении:** сообщение теста называет метрику и нарушителя; сырые цифры —
`qa/reports/load/acceptance_*.json`, память по минутам —
`qa/reports/load/acceptance_memory.jsonl`. Проверки независимы (каждая — своя
копия стенда), упавшую можно повторить одной: `ACCEPTANCE=1 uv run pytest
qa/test_acceptance_<тест>.py -v`. Если не уложились в 30 с на «Остановке» —
порог пересматривается до 60 с (SPEC §22).

### Выдержки: первый полный прогон (2026-11-14, стенд `--scale three-years`)

Все шесть проверок и регрессия — PASS, полный прогон 1 ч 3 мин. Деградации нет
(медианы последних 10 операций в пределах ×1,5), память за час не растёт
(наклон RSS обоих процессов ≈ 0 МБ/мин). Окно конкуренции нашло узкое место —
один процесс кабинета сериализует CPU-рендер (p95 ~3,9 с при 100
одновременных); закрыто батчингом заключений (N+1 → один запрос) и вторым
uvicorn-воркером (`--workers 2`, прод-конфигурация).
