# Свой период в выгрузках бота — вопросы (2026-11-18)

**Контекст.** Находка автора: «в боте когда делаем выгрузку в пдф нет возможности выбора
своего периода». Сейчас в боте вопрос «За какой период выгрузить?» даёт только три
кнопки — «7 дней» / «30 дней» / «всё время» (PDF — §10.1, CSV — §10); callback'и
`pdf:7` / `pdf:30` / `pdf:all` и `csv:7` / `csv:30` / `csv:all`. Свой период есть у
статистики («📆 Свой период», инлайн-календарь, §6.5, 0.5.3: первый тап — начало,
второй — конец, обратный порядок дат меняется местами, будущее запрещено, длина ≤ 31
дня) и в ЛК (период задаётся фильтрами `date_from`/`date_to` — выгрузки ЛК за
произвольный период уже работают). Ответы вписать в строки «Ответ:».

## R1. Объём: только PDF или и CSV

- **А)** Только PDF — как в находке.
- **Б)** PDF и CSV: у обеих выгрузок один вопрос периода и один календарь — паритет
  с ЛК (там обе выгрузки за произвольный период) и меньше кода: общий сценарий
  выбора, а не второй на PDF.

Рекомендация: **Б**.

Ответ: **Б** (утверждено 2026-11-18). Сценарий выбора периода один, различаются
только финальные действия; только PDF пришлось бы потом дорабатывать для CSV.
Колбэки унифицированы: `pdf:custom` и `csv:custom` с общим обработчиком
календаря и параметром «куда вернуться с выбранными датами».

## R2. Как выбирать период

- **А)** Переиспользовать календарь «Свой период» из статистики (§6.5): тот же
  инлайн-календарь с листанием месяцев, первый тап — начало, второй — конец; в
  крупном режиме — недельный вид (UI12, UI19). Уже проверен сценарий, единообразно
  с «📊 Статистика».
- **Б)** Свой ввод дат (калькулятор/текст) — второй календарь в коде, расходится с
  каноном «кнопки вместо свободного ввода».

Рекомендация: **А**.

Ответ: **А** (утверждено 2026-11-18). Календарь §6.5 переиспользуется (порядок
тапов, смена дат местами, запрет будущего, крупный режим UI12/UI19) — для
пользователя единообразие со статистикой важнее гибкости. Календарь
параметризуется: сценарий (статистика, PDF, CSV) и его правила — иначе он
тащит за собой логику статистики.

## R3. Лимит длины своего периода

- **А)** 31 день — как в статистике (§6.5, единое правило календаря).
- **Б)** Без лимита длины: ограничение — только существующий лимит 5000 записей
  (§10.1: «Слишком много записей, выберите период поменьше»); «всё время» и так
  выгружает всё, длинный свой период (например, квартал) ничего не ломает.

Рекомендация: **Б**.

Ответ: **Б** (утверждено 2026-11-18). Реальный сценарий PDF — отчёт врачу «с
прошлого визита» (1–3 месяца), лимит 31 день его сломает; нагрузка не растёт
(«всё время» и так выгружает всё). Лимит 31 день остаётся в статистике, для
выгрузок максимальная длина — «нет ограничения» (та же параметризация, что в
R2). При ошибке «Слишком много записей, выберите период поменьше» — сразу
выбрать другой период (кнопки «Изменить период» / «Назад»), а не обрывать
сценарий.

## R4. Что происходит после выбора дат

- **А)** Сразу генерация: сообщение с вопросом/календарём редактируется на
  «Готовлю отчёт…», затем файл — как сейчас после «7 дней» (минимум трения).
- **Б)** Шаг подтверждения: «Период: 12.10–20.10 (9 дней)» с кнопками «Выгрузить» /
  «Изменить» / «Назад».

Рекомендация: **А**.

Ответ: **А** (утверждено 2026-11-18). Ошибка дешёвая (лишний файл → повторная
выгрузка), шаг подтверждения добавил бы тап к двум тапам по календарю. В
«Готовлю отчёт…» указывается период («Готовлю отчёт за 12.10–20.10…») — это даёт
эффект подтверждения без лишнего тапа. Если за период нет записей — сообщить и
предложить выбрать другой период, а не отправлять пустой файл.
