# Задача: Разработать полный набор нагрузочных тестов для Telegram-бота «Дневник гипертоника»

## Контекст

Ты — senior Python-разработчик и QA-инженер. Проект — Telegram-бот для гипертоников с веб-кабинетом (пациент), кабинетом врача, админ-панелью и планировщиком напоминаний. Стек: Python 3.11+, aiogram 3.x, SQLAlchemy 2.0 async, SQLite (WAL), APScheduler 3.x, FastAPI + Jinja2, uv, pytest, Docker.

Внимательно прочитай `SPEC.md` и `TZ.md` в корне репозитория. **Все требования ниже основаны на этих документах.** Если что-то в них противоречит промпту — приоритет у `SPEC.md`.

## Цель

Написать набор нагрузочных тестов, который доказывает: система **стабильно работает при 20 одновременных активных пользователях** и **базе на 5000 записей измерений** (плюс соответствующие объёмы лекарств, логов, напоминаний, врачей) без потери корректности данных, без 5xx/429 и без дублей.

Нагрузочный тест должен покрывать **все аспекты функционала**:
- Telegram-бот (запись давления, правка, лекарства, напоминания, архив).
- Личный кабинет пациента (FastAPI).
- Кабинет врача (FastAPI).
- Админ-панель (Telegram).
- APScheduler (100+ активных job'ов).
- Фоновое резервное копирование.
- Одновременные конкурентные операции (двойные нажатия, повторы).

## Ограничения

1. **Только тестовый стенд.** Нагрузочные аккаунты и данные не должны попадать в прод-БД. Все скрипты запускаются на отдельной БД `data/test-stand.sqlite3` и отдельном инстансе бота (`BOT_TOKEN` тестового бота).
2. **Без реального Telegram API** — кроме явно помеченного «живого флешмоба». Для эмуляции 20 виртуальных ботов используй `aiogram` с `MockedBot` или напрямую вызывай хендлеры (см. `tests/conftest.py`).
3. **Никаких деструктивных операций** с прод-БД. Пароли нагрузочных аккаунтов — только из env (`LOAD_PASSWORD`), в коде не хранить.
4. **Идемпотентность запуска:** повторный прогон не должен падать из-за уже существующих данных (сид должен быть очищаемым или проверять существование).
5. **CI-совместимость:** лёгкие burst-тесты (п.3) должны запускаться через `pytest qa/` **без Docker** на in-memory SQLite. Полные тесты (Locust, 5000 записей) — только по флагу `LOAD_TEST=1`.

## Что должен покрыть тест (обязательный список)

### 1. Сид данных (5000 записей)
- **20 пациентов**, у каждого `web_users` запись (Argon2id-хеш, пароль из `LOAD_PASSWORD`).
- **5000 измерений** (250/пациент), распределены по 30 последним дням, времена в таймзоне пользователя, значения в валидных диапазонах (`sys 100-180`, `dia 60-110`, `pulse 50-110`).
- **100 лекарств** (5 на пациента, по 1-2 слота каждое, включая `crisis`).
- **500 medication_logs** (по 25 на пациента, статусы `taken`/`skipped`/`partial`).
- **100 активных reminders** (утренние/обеденные/вечерние слоты у 20 пользователей, `next_trigger_time` в ближайший час).
- **20 врачей** + `doctor_patients` связи со статусом `active` к пациентам 1:1.
- **1 admin** (`ADMIN_TELEGRAM_IDS`).

### 2. HTTP-кабинет пациента (Locust, `qa/locustfile.py`)
- **20 виртуальных пользователей**, ramp-up 2/сек, длительность 5 минут.
- Сценарий (с весами):
  - 40%: вход → просмотр дашборда (графики, 3 canvas) → логаут
  - 20%: история записей с фильтром 30 дней
  - 15%: экспорт CSV (30 дней)
  - 10%: добавление измерения (валидные данные, время = now − 1 час)
  - 10%: настройки профиля → сохранение
  - 5%: добавление лекарства
- **Критерии:** 0 ответов 5xx; 0 ответов 429; p95 дашборда < 2 с; p95 CSV < 3 с.

### 3. Сервисный слой (pytest burst, `qa/test_load_burst.py`, `LOAD_TEST=1`)
- 20 пользователей × 50 конкурентных операций `asyncio.gather` на **файловой** SQLite (не in-memory!) с PRAGMA продакшена (WAL, busy_timeout=5000, foreign_keys=ON).
- Сценарии:
  - массовая запись измерений (20 × 50 = 1000 записей);
  - двойные нажатия «Записать давление» (идемпотентность дедупа);
  - конкурентные правки одной и той же записи;
  - одновременные «Принял всё ✓» на одном слоте (ровно одна транзакция логов);
  - параллельные `/start` от одного пользователя (get-or-create).
- **Критерии:** нет `OperationalError: database is locked` (с учётом retry), нет дублей измерений за минуту, все операции завершаются, время прохождения < 60 с.

### 4. Telegram-бот (pytest burst, `qa/test_load_bot.py`)
- 20 виртуальных пользователей (моки aiogram `Bot`, `Message`, `CallbackQuery`, фикстура в `conftest.py`).
- Каждый прогоняет полный флоу:
  - `/start` → онбординг (или главное меню, если уже onboarded).
  - 10 записей давления калькулятором (`m:key:*` → `m:key:ok`).
  - правка последней (`m:edit`) × 3.
  - «Приняли лекарство?» → «Да» → мультивыбор лекарств → «Готово».
  - «Дневник за сегодня».
  - «Статистика» 7 дней и 30 дней.
  - Экспорт CSV.
- **Критерии:** все 20 пользователей проходят флоу без исключений; после прогона в БД ровно 20 × (10 + правки) измерений, без дублей; `measurement_medications` заполнена.

### 5. Кабинет врача (pytest burst, `qa/test_load_doctor.py`)
- 20 врачей заходят по magic link одновременно (`/doctor/login`), каждый открывает дашборд своего пациента.
- 5 запросов CSV и PDF на врача.
- 3 комментария (`doctor_notes`) на врача.
- **Критерии:** все 200 запросов успешны; p95 дашборда < 2 с; комментарии корректно привязаны к `doctor_id`/`user_id`.

### 6. Напоминания (pytest, `qa/test_load_reminders.py`)
- 100 активных reminders в БД с `next_trigger_time = now + 1s`.
- Планировщик запущен, ловим 100 отправок в мок `Bot.send_message`.
- **Критерии:**
  - ровно 100 сообщений (не больше, не меньше);
  - нет дублей по `(user_id, type)`;
  - `last_sent_date` обновлён у всех;
  - все `next_trigger_time` пересчитаны на завтра;
  - двойной тик планировщика не отправляет повторно.

### 7. Бэкап под нагрузкой (pytest, `qa/test_load_backup.py`)
- Запустить `services.backup.create_backup()` во время burst-нагрузки (20 × 50 записей).
- **Критерии:** бэкап создан; `PRAGMA integrity_check` = `ok`; размер соответствует ожидаемому; основной поток не заблокирован дольше 5 секунд (WAL справляется).

### 8. Конкурентные гонки (pytest, `qa/test_load_concurrent.py`)
Явные сценарии гонок из `SPEC.md §7.2`:
- Параллельные `save_measurement` одного пользователя с одинаковыми данными → одна запись.
- Параллельные `med_remeasure` на одном `measurement_id` → ровно один job в APScheduler.
- Параллельные «Принял всё ✓» на слот → ровно N записей `medication_logs`, не 2N.
- Параллельные правки одной записи → последняя победила, `timestamp` не изменился.
- Параллельные `/start` → одна `users` строка.

### 9. Живой флешмоб (документировать в `qa/README.md`)
Раздел «Ручной сценарий для 20 реальных аккаунтов» — чек-лист для команды QA:
1. Каждый участник регистрируется в тестовом боте.
2. Проходит онбординг (таймзона `Europe/Minsk`, цель 130/80).
3. Делает 5 записей давления.
4. Добавляет 2 лекарства.
5. Проверяет напоминание (через `m:rem:snooze`).
6. Экспортирует CSV.
7. Владелец аккаунта проверяет, что в БД ровно 100 измерений и 40 лекарств.
8. Длительность сценария ≤ 10 минут, все действия параллельно (созвон / общий чат).

## Критерии приёмки (обязательно реализовать как `test_load_regression.py`)

После полного прогона `LOAD_TEST=1 pytest qa/` система обязана соответствовать:

| Метрика | Порог | Как проверить |
|---|---|---|
| HTTP 5xx | 0 | парсинг Locust CSV |
| HTTP 429 | 0 | парсинг Locust CSV |
| p95 дашборда | < 2000 мс | Locust CSV |
| p95 CSV за 30 дней | < 3000 мс | Locust CSV |
| Дублей измерений за минуту | 0 | `SELECT COUNT(*)` с группировкой |
| Дублей `medication_logs` за слот/день | 0 | SQL-проверка |
| Дублей отправленных напоминаний | 0 | подсчёт мок-вызовов |
| `integrity_check` после бэкапа | `ok` | PRAGMA |
| Все 20 пациентов живы в `users` | 20 | SQL |
| Все 5000 измерений на месте | 5000 | SQL |

Если хоть один критерий не выполнен — `test_load_regression.py` падает с понятным сообщением и id нарушителя.

## Запуск (обязательно описать в `qa/README.md`)

```bash
# 1. Сид тестового стенда (5000 записей, 20 пациентов, врачи, напоминания)
LOAD_PASSWORD='<пароль>' \
    uv run python qa/seed/seed_all.py --db data/test-stand.sqlite3

# 2. Burst сервисного слоя (быстрый, без Docker)
LOAD_TEST=1 uv run pytest qa/test_load_burst.py -v -s

# 3. Полный набор burst-тестов
LOAD_TEST=1 uv run pytest qa/ -v -s --ignore=qa/locustfile.py

# 4. HTTP-нагрузка кабинета (требует запущенный uvicorn)
LOAD_PASSWORD='<пароль>' \

    -u 20 -r 2 -t 5m --headless \
    --csv=qa/reports/load/locust

# 5. Регрессия критериев приёмки
uv run pytest qa/test_load_regression.py -v

Правила кода
Типизация, docstrings на русском.

Не дублировать фикстуры — общие в qa/conftest.py.

Параметризация вместо копипаста (20 пользователей = @pytest.mark.parametrize("user_idx", range(20))).

Изоляция: каждый тест начинает с чистой БД (tmp_path / in-memory) или явно чистит test-stand.sqlite3 перед собой.

Никаких time.sleep — только asyncio.sleep, asyncio.gather, Event.

Логи с контекстом: logging.getLogger("qa.load"), структурированные (user_id, op, duration_ms).

Проверки с сообщениями: assert len(rows) == 250, f"user {uid}: expected 250, got {len(rows)}".

Что НЕ надо делать
Не писать тесты на каждый юнит-хендлер — это уже в tests/. Здесь только нагрузка и гонки.

Не пытаться реально прогнать 20 ботов через Telegram API (это заблокирует аккаунт). Только моки.

Не менять код бота/кабинета — если для нагрузочного теста нужен хук, добавь его в тестовую фикстуру, а не в прод-код.

Не добавлять зависимости в прод — только в [project.optional-dependencies].load (locust, httpx, pytest-html, playwright).
