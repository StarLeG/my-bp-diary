# ЛК: выбор лекарств в форме измерения — вопросы перед планом

Запрос: в форме «➕ Добавить измерение» личного кабинета при отмеченной галочке «Принял лекарство» показывать поля выбора лекарств.

Сверено с `doc/SPEC.md`: §4.4 (`medications`), §4.5 (`medication_logs`), §4.11 (`measurement_medications`), §6.3 (мультивыбор в боте), §7.2 (идемпотентность), §16.2 (форма ЛК), а также с `web/cabinet/app.py` и `templates/dashboard.html`.

**Как отвечать:** впишите в строку «Ответ» букву варианта (или свой вариант). «Моё мнение» — только мнение, решаете вы. Код не пишу, пока нет ответов. Первым шагом после ответов — правка SPEC §16.2, затем код и тесты.

### M1. Что записывает выбор лекарств из ЛК

**Контекст.** Сейчас в SPEC §16.2 сказано: «Добавление и правка из ЛК … не создают `medication_logs` — только запись и её поля (флаг „Принял лекарство“ — исторический)». В боте «Готово» мультивыбора создаёт и `medication_logs` (они попадают в приверженность §6.5 и в экспорт приёмов §10), и связи `measurement_medications` (это перечень в колонке «лекарство» истории, §16.2). Для архивных записей бот `medication_logs` не создаёт (§6.10). Записи из ЛК чаще всего задним числом.

- **А** — только связи `measurement_medications`. В истории появляется «Принято: Лозартан 50 мг, …», приверженность и экспорт приёмов не меняются. В SPEC правило «ЛК не создаёт `medication_logs`» остаётся.
- **Б** — как в боте: связи плюс `medication_logs` (`status='taken'`, слот — из лекарства, время — момент измерения). Повтор за те же локальные сутки новых записей не даёт (§7.2). Правило SPEC §16.2 меняется; приверженность начинает учитывать записи из ЛК, в том числе задним числом.
- **В** — связи всегда, а `medication_logs` только если момент измерения попадает в текущие локальные сутки пользователя (по аналогии с архивом в боте).

**Моё мнение:** А — минимальное изменение, не трогает статистику приверженности и не порождает задним числом приёмы, которые нельзя отличить от отмеченных вовремя.

### M2. Какие лекарства показывать

**Контекст.** Лекарство в БД — пара «название + слот» (`morning`/`noon`/`evening`/`crisis`, UNIQUE(user_id, name, slot)), одно название может быть в нескольких слотах. В боте мультивыбор показывает все приёмы кнопками «Лозартан 50 мг · утро».

- **А** — все лекарства пользователя, сгруппированные по слотам («Утро», «Обед», «Вечер», «Кризис») как в личной карточке, по чекбоксу на строку «Название дозировка».
- **Б** — плоский список чекбоксов «Лозартан 50 мг · утро», как кнопки бота.
- **В** — только лекарства слота, соответствующего времени измерения, плюс «Кризис».

**Моё мнение:** А — совпадает с карточкой и читается лучше длинного плоского списка; В ломается, если поменять время в форме.

### M4. Форма правки («✏️»)

**Контекст.** Сейчас правка из ЛК меняет флаг `medication_taken`; связи `measurement_medications` правка значений не трогает (§4.11). Связи записи могут быть созданы ботом.

- **А** — в форме правки показывать тот же выбор с отмеченными текущими связями; сохранение заменяет набор связей (добавляет и снимает). Снятая галочка «Принял лекарство» снимает все связи записи.
- **Б** — как А, но снятая галочка связи не трогает (только флаг).
- **В** — выбор лекарств только при добавлении; правка связи не показывает и не меняет.

**Моё мнение:** А — иначе в истории останется «Принято: …» у записи, где галочка снята. Если по M1 выбрано Б/В, снятие связи `medication_logs` не удаляет (как удаление записи сейчас, §16.2).

## Ответы первого раунда (2026-11-08)

- **M1 — Б.** Как в боте: связи `measurement_medications` плюс `medication_logs` (`status='taken'`, время — момент измерения), они влияют на приверженность, в том числе для архивных дат. В SPEC §16.2 убрать «не создают `medication_logs`» и записать: «Выбор лекарств в ЛК работает так же, как в боте: создаёт связи `measurement_medications` и записи `medication_logs` (со статусом taken и соответствующим временем), влияя на приверженность».
- **M2 — А.** Группы по слотам («Утро», «Обед», «Вечер», «Кризис»), как в «Личной карточке».
- **M3 — Б.** Предотметка по времени измерения: запись на 08:00 — отмечены лекарства слота «Утро»; если время не совпадает ни с одним слотом, ничего не отмечается.
- **M4 — А с откатом.** В правке показываются текущие связи с галочками. При сохранении — разница: добавленные галочки дают новые связи и журнал, снятые — удаляют связь и соответствующий `medication_logs` этой записи. Снятая галочка «Принял лекарство» снимает всё.
- **M5 — А.** «У вас пока нет добавленных лекарств» + inline-ссылка «Перейти в Управление лекарствами».
- **Допущения 1–6 подтверждены.** Версия — 0.4.5.

## Второй раунд: уточнения по ответам

### N1. Как время измерения соотносится со слотом (M3)

**Контекст.** В коде нет правила «время → слот». Есть время напоминаний пользователя (`reminders.local_time` для `morning`/`noon`/`evening`; умолчания `DEFAULT_SLOT_TIMES` — 08:00 / 13:00 / 21:00), а у слота «Кризис» времени нет. Ответ M3 предполагает, что бывают времена вне всех слотов.

- **А** — окно ±2 ч вокруг времени слота пользователя (из `reminders`, если слот не настроен — умолчание). Например, при умолчаниях: 06:00–10:00 — утро, 11:00–15:00 — обед, 19:00–23:00 — вечер, остальное — ничего. Окна, если пересекаются, делятся пополам.
- **Б** — фиксированные диапазоны без учёта настроек, с разрывами: 05:00–10:59 утро, 11:00–15:59 обед, 18:00–23:59 вечер, остальное — ничего.
- **В** — ближайший слот пользователя без разрывов (тогда «ничего» не бывает — расходится с M3).

«Кризис» не предотмечается никогда — подтвердите.

**Моё мнение:** А — уважает реальное расписание пользователя; ширину окна (±2 ч) — на ваше усмотрение.

### N2. Предотметка при смене даты/времени в форме

**Контекст.** Без JS предотметку можно посчитать только при открытии формы (время по умолчанию — текущее). Если пользователь поменяет время на 08:00, галочки сами не сменятся.

- **А** — только при открытии формы, без JS (как согласовано для скрытия блока).
- **Б** — небольшой JS в `static/`: при смене времени пересчитывать предотметку, пока пользователь сам не трогал галочки лекарств. Без JS работает как А.

**Моё мнение:** Б — иначе M3 срабатывает только для записи «сейчас», а для «08:00 вчера» нет.

### N3. Какой `medication_logs` откатывать при снятой галочке (M4)

**Контекст.** У `medication_logs` нет ссылки на запись измерения. Журнал дедуплицируется по локальным суткам (§7.2): если приём за эти сутки уже отмечен (например, «Принял всё ✓» по напоминанию в 08:05), ЛК новую строку не создаст — а связь создаст. Бот при «Готово» пишет журнал с моментом нажатия, а не с моментом измерения, так что у связей, созданных ботом, журнал с другим временем.

- **А** — удалять журнал этого лекарства с `timestamp` **ровно** равным моменту записи (только то, что создал ЛК). Журналы бота и напоминаний не трогаются, даже если связь снята.
- **Б** — удалять журнал этого лекарства и слота за те же локальные сутки, что и запись (любой источник: ЛК, бот, напоминание). Снимет и «Принял всё ✓» за тот день.
- **В** — точная связь в схеме: колонка `medication_logs.measurement_id` (nullable, FK, `SET NULL`) + миграция; удаляется только журнал, созданный для этой записи (и ботом, и ЛК). Меняет схему из CLAUDE.md/SPEC §4.5.

**Моё мнение:** А — не удаляет отметки, сделанные в другом месте; цена — после снятия в боте созданной связи журнал бота остаётся.

**Ответ:**

### N4. Правка момента записи с уже отмеченными лекарствами

**Контекст.** В ЛК `timestamp` при правке меняется (§16.2). Журнал, созданный с прежним моментом, остаётся в прежних сутках.

- **А** — переносить журналы этой записи (по правилу N3) на новый момент; если в новых сутках приём уже отмечен — старый журнал удалить (дедуп §7.2).
- **Б** — не переносить: журнал остаётся на старом моменте, новые галочки пишутся на новый.

**Моё мнение:** А — иначе приверженность считает приём не в тот день.

**Ответ:**

### N5. Удаление записи

**Контекст.** Сейчас SPEC §16.2: при удалении записи связи удаляются каскадом, `medication_logs` не затрагиваются. При M4 с откатом это расходится: снять галочку — журнал удаляется, удалить запись целиком — нет.

- **А** — при удалении записи удалять и её журналы (по правилу N3).
- **Б** — оставить как есть (журнал при удалении записи сохраняется).

**Моё мнение:** А — единообразно с откатом в M4.

### N6. Архивные записи в боте

**Контекст.** M1 Б: ЛК пишет журнал и для прошлых дат. Бот для архивных записей (§6.10, CLAUDE.md) журнал не создаёт и мультивыбор не показывает — после изменения бот и ЛК будут вести себя по-разному для архива.

- **Б** — отдельной задачей привести бот к ЛК (меняет §6.10 и CLAUDE.md, вне этой ветки).

**Моё мнение:** А в этой ветке; Б — если нужно, отдельно.

## Ответы второго раунда (2026-11-08)

- **N1.** Ближайший слот в пределах ±2 ч: среди «Утро» / «Обед» / «Вечер», чьё время в окне, — ближайший; ни одного — ничего не отмечено. Время — `reminders.local_time`; напоминание выключено или записи нет — умолчание 08:00 / 13:00 / 21:00. «Кризис» не предотмечается никогда.
- **N2 — Б.** Небольшой inline-скрипт пересчитывает предотметку при смене времени; без JS — только при открытии формы.
- **N3 — А.** Откатывается только журнал с точным моментом записи. Кабинет пишет `medication_logs` с `timestamp = measurements.timestamp`; связь журнала с записью — пара `medication_id + timestamp`.
- **N4 — А.** При смене момента журнал записи переносится на новый момент в той же транзакции.
- **N5 — А.** При удалении записи сначала удаляется её журнал (по паре), затем запись.
- **N6 — А.** Бот не меняем; различие — в SPEC §6.10, §16.2 и §17.
- Допущения подтверждены, включая fallback на умолчания времени слотов и `timestamp` журнала = моменту записи.

## Допущения на подтверждение

1. Показ/скрытие — без JavaScript, через CSS (`:has(input[name=medication_taken]:checked)`); без поддержки `:has` блок просто виден всегда. Сервер учитывает выбор только при отмеченной галочке.
2. Выбор лекарства без галочки невозможен; при отмеченной галочке выбор необязателен (только флаг, как сейчас).
3. Чужой или несуществующий id лекарства — ошибка формы «Лекарство не найдено», запись не создаётся (§7.1 — чужое выглядит как отсутствующее).
4. Двойная отправка формы: дубль измерения отсекается как сейчас («Это давление уже записано»), связи дублей не создают (UNIQUE).
5. Импорт CSV и кабинет врача не меняются (врач уже видит перечень в истории).
6. Версия — PATCH (совместимое дополнение в 0.x), номер — при релизе по скилу `semver`.
