# Приглашение врача: отправка ссылки на e-mail и добавление по Telegram — вопросы перед планом

Запрос:
1. Сейчас после ввода e-mail врача бот только показывает ссылку пациенту — на указанный e-mail ничего не уходит. Нужно отправлять.
2. Добавить приглашение врача по имени пользователя Telegram.

Сверено с `doc/SPEC.md` §3 (переменные окружения), §4.8–4.9 (`doctors`, `doctor_patients`), §8 (FSM), §16.2 («SMTP не настраиваем»), §21 (кабинет врача); с кодом `bot/handlers/doctor.py`, `bot/services/doctor.py`, `web/cabinet/doctor_auth.py`, `web/cabinet/app.py` (маршруты `/doctor*`), `bot/db.py` (миграции), `bot/handlers/start.py` (`/start` с параметром), лендингом (FAQ).

**Как отвечать:** впишите букву варианта (или свой вариант) в строку «Ответ». «Моё мнение» — только мнение, решение за вами. Код не пишу, пока не будут даны все ответы и вы не утвердите правки SPEC.

## Что есть сейчас (факты из кода)

1. **SMTP в проекте нет вообще.** SPEC §21 п.3 разрешил MVP «генерировать ссылку и отправлять её пациенту, чтобы он переслал врачу», §16.2 — «SMTP не настраиваем». Поэтому письмо и не уходит.
2. **Ссылка живёт 15 минут и одноразовая** (`DOCTOR_TOKEN_MAX_AGE`, `jti`). Пересланная пациентом ссылка часто протухает, пока врач её откроет.
3. **Пароль врача случайный, врач его не знает.** Форма `/doctor/login` (e-mail + пароль) есть, но войти через неё врач не может: только по свежей ссылке от пациента, дальше — сессия 7 дней.
4. **Имя врача** = часть e-mail до «@» (`ivanova` для `ivanova@clinic.by`), поле `doctors.name` NOT NULL.
5. **Один врач на пациента**: пока есть связь `pending`/`active`, добавить второго нельзя.
6. **Лендинг уже обещает** (FAQ, раздел про врача): «Там же можно добавить e-mail врача, чтобы он получал доступ без пересылки ссылок» — сейчас это неправда.
7. **Ограничения Telegram для «добавления по @username»:**
   - Bot API не умеет найти человека по `@username`: бот знает только тех, кто сам ему писал, и только если сохранил их username (в `users` username сейчас не хранится).
   - Бот не может первым написать человеку, который ни разу не нажимал «Старт» у бота.
   - Username можно сменить или не иметь вовсе.

   Отсюда: врач в любом случае должен хотя бы раз открыть бота.

## Часть E. Отправка ссылки на e-mail

### E1. Через что отправлять письма

**Контекст.** Своего почтового сервера на `185.23.239.253` нет. Порт 25 у хостеров часто закрыт, поэтому нужен внешний SMTP (порт 465/587) или HTTP-API почтового сервиса.

- **А** — SMTP почтового ящика на вашем домене (например, Яндекс 360 / Mail.ru для бизнеса для `electroman.by`) — `noreply@electroman.by`.
- **Б** — транзакционный сервис по SMTP (Unisender Go, Mailgun, Brevo и т.п.) — бесплатного тарифа хватит.
- **В** — SMTP обычного личного ящика (Gmail/Яндекс с паролем приложения).
- **Г** — свой вариант.

**Моё мнение:** А или Б — письма с собственного домена реже попадают в спам. В — проще всего, но письмо «от частного ящика» с ссылкой выглядит подозрительно, и есть дневные лимиты.

**Ответ:** А — SMTP своего домена, noreply@electroman.by.

### E2. Адрес отправителя и DNS

**Контекст.** Чтобы письма не уходили в спам, у домена отправителя нужны DNS-записи SPF, DKIM (и желательно DMARC) в панели domain.by — их выдаёт выбранный в E1 сервис.

- **А** — отправитель `Дневник гипертоника <noreply@electroman.by>`; записи SPF/DKIM/DMARC в domain.by добавляете вы, я готовлю точный список.
- **Б** — другой адрес/имя отправителя (укажите).

**Моё мнение:** А.

**Ответ:** А — отправитель «Дневник гипертоника <noreply@electroman.by>»; SPF/DKIM/DMARC в domain.by настраивает пользователь по подготовленному списку.

### E3. Настройки почты

Предлагаемые переменные окружения (§3), все опциональные:

```
SMTP_HOST, SMTP_PORT (465 / 587), SMTP_USER, SMTP_PASSWORD,
SMTP_FROM («Дневник гипертоника <noreply@electroman.by>»), SMTP_SECURITY (ssl | starttls)
```

- **А** — так; если `SMTP_HOST` пуст — письма не отправляются, бот работает как сейчас (ссылка пациенту для пересылки).
- **Б** — свой состав (укажите).

**Моё мнение:** А — локальный и QA-стенд работают без почты, как сейчас.

**Ответ:** А — переменные из списка; пустой SMTP_HOST — письма не отправляются, бот работает как сейчас.

### E4. Библиотека отправки

- **А** — стандартный `smtplib` в `asyncio.to_thread` (§7.2 п.7), без новых зависимостей.
- **Б** — `aiosmtplib` (асинхронная, новая зависимость).

**Моё мнение:** А — писем мало, лишняя зависимость не нужна.

**Ответ:** А — smtplib в asyncio.to_thread, без новых зависимостей.

### E5. Когда отправлять письмо

Можно выбрать несколько.

- **1** — при добавлении врача по e-mail (приглашение).
- **2** — при «Отправить отчет» из главного меню, если у врача есть e-mail.
- **3** — при повторном добавлении того же врача после отзыва.

**Моё мнение:** 1 + 2 + 3: «Отправить отчет» — это и есть «отправить ссылку врачу».

**Ответ:** 1 + 2 + 3 — при добавлении, при «Отправить отчет», при повторном добавлении.

### E6. Срок жизни ссылки в письме

**Контекст.** Сейчас 15 минут и одноразовая. Письмо врач может открыть через день.

- **А** — для письма: 72 часа, одноразовая (повторный клик после входа — «Ссылка уже использована, войдите по паролю / попросите новую»).
- **Б** — 7 дней, одноразовая.
- **В** — 24 часа, одноразовая.
- **Г** — оставить 15 минут.

Ссылка, которую бот показывает пациенту для пересылки, — **Д** оставить 15 минут / **Е** тот же срок, что в письме.

**Моё мнение:** А + Е — одинаковое правило для обоих путей, 72 часа покрывают выходные.

**Ответ:** А (72 часа) + Е (тот же срок для ссылки-пересылки).

### E7. Что видит пациент после ввода e-mail

- **А** — «Приглашение отправлено на {email}» + та же ссылка для пересылки (на случай, если письмо не дойдёт).
- **Б** — только «Приглашение отправлено на {email}», без ссылки.
- **В** — как сейчас (только ссылка), письмо уходит молча.

**Моё мнение:** А — письмо может уйти в спам, а пересылка в мессенджер — привычный запасной путь.

**Ответ:** А — сообщение «Отправлено» + та же ссылка для пересылки.

### E8. Ошибка отправки

- **А** — письмо не ушло (SMTP недоступен, адрес отвергнут) — пациент видит «Не удалось отправить письмо. Перешлите врачу ссылку сами:» + ссылка; в лог — ошибка без адреса и токена. Повторов нет.
- **Б** — А + до 3 повторов с паузой, пациенту — сообщение после результата.

**Моё мнение:** А — пациент сразу знает, что делать; повторы задерживают ответ бота.

**Ответ:** А — «Не удалось отправить» + ссылка, без повторов.

### E9. Защита от спама через бота

**Контекст.** Любой пользователь бота может ввести чужой e-mail — бот станет рассылать письма на произвольные адреса.

- **А** — не больше 3 писем на пациента в сутки и не больше 1 письма на один адрес в час; сверх лимита — «Письмо уже отправлено недавно. Перешлите ссылку сами:» + ссылка.
- **Б** — свои лимиты (укажите).
- **В** — без лимитов.

**Моё мнение:** А. Лимиты считаются по таблице отправок (см. E10).

**Ответ:** А — 3 письма в сутки на пациента, 1 в час на адрес.

### E10. Учёт отправленных писем

- **А** — новая таблица `email_log` (user_id, email, kind, sent_at, ok) — для лимитов E9 и админки; адреса чистятся при удалении аккаунта (§19).
- **Б** — лимиты в памяти процесса (сбрасываются при рестарте), без таблицы.

**Моё мнение:** А — лимит переживает перезапуск, и видно, доходят ли письма.

**Ответ:** А — таблица email_log. **Заменено ответом N7-В:** вместо `email_log` — единая таблица `invite_log` (поля `channel` = `email` / `telegram` и `target`); лимиты E9 действуют для обоих каналов.

### E11. Текст письма

Черновик (утверждается дословно):

```
Тема: Пациент открыл вам доступ к дневнику давления

Здравствуйте!

Пациент {имя} открыл вам доступ к своему дневнику давления
в «Дневнике гипертоника».

Посмотреть измерения, графики и отчёт:
{ссылка}

Ссылка действует {срок} и открывает доступ один раз.
Если вы не знаете этого пациента — просто не открывайте ссылку,
доступ без вашего входа не появится.

—
Дневник гипертоника · https://bp-diary.electroman.by
```

- **А** — так, простым текстом.
- **Б** — так, но HTML-письмо с кнопкой (и текстовая версия).
- **В** — свой текст (впишите).

`{имя}` — **Г** имя из Telegram (`first_name`, как сейчас в сообщении для пересылки) / **Д** без имени («Ваш пациент открыл…»).

**Моё мнение:** Б + Г. Имя нужно, чтобы врач понял, от кого письмо; оно уже есть в сообщении для пересылки.

**Ответ:** А (только текст) + Г (имя из Telegram). HTML-письма чаще попадают в спам — plain text надёжнее.

### E12. Вход врача без пароля

**Контекст.** Факт 3: врач не знает пароля. С почтой появляется возможность входа по e-mail.

- **А** — на `/doctor` кнопка «Получить ссылку для входа на e-mail»: врач вводит e-mail, если такой врач есть — письмо со ссылкой (15 минут); ответ одинаковый для любого адреса (не раскрывает, есть ли врач). Те же лимиты E9.
- **Б** — в кабинете врача — «Задать пароль» (после входа по ссылке).
- **В** — А + Б.
- **Г** — не сейчас, отдельной задачей.

**Моё мнение:** Г — это расширение кабинета, а не просьба «отправлять письмо»; но без него врач после 7 дней сессии снова зависит от пациента. Если делать — В.

**Ответ:** Г — отдельной задачей. Сейчас главное — доставить письмо и внедрить Telegram-приглашения; вход врача по e-mail требует отдельного продумывания (токены, сессии).

## Часть T. Добавление врача по Telegram

### T1. Как устроить приглашение

**Контекст.** Факт 7: найти человека по `@username` бот может, только если этот человек раньше открыл бота и бот запомнил его username.

- **А** — **по @username**: врач однажды открывает бота и регистрируется как врач (см. T3); пациент вводит `@username` → бот находит врача и сам присылает ему приглашение в Telegram. Если не найден — «Врач ещё не открывал бота. Перешлите ему ссылку:» + ссылка-приглашение (вариант Б).
- **Б** — **ссылка-приглашение в бота** без ввода username: пациент нажимает «Пригласить врача в Telegram», получает ссылку `https://t.me/my_bp_diary_bot?start=doc_<код>` и пересылает её врачу в Telegram; врач нажимает «Старт» — бот привязывает его как врача пациента. Username не нужен вовсе.
- **В** — оба: Б — основной путь, А — для врачей, уже зарегистрированных в боте.

**Моё мнение:** В. Б работает всегда (даже без username и для врача, который бота ещё не видел); А удобен, когда врач уже есть в боте — например, у него несколько пациентов.

**Ответ:** В — оба способа: ссылка-приглашение (Б) — основной, поиск по @username (А) — для зарегистрированных врачей. Ссылка работает всегда, поиск — бонус для тех, кто уже в системе.

### T2. Срок жизни ссылки-приглашения в бота (если Б или В в T1)

- **А** — 72 часа, одноразовая (как E6-А).
- **Б** — 7 дней, одноразовая.
- **В** — свой срок.

**Моё мнение:** А — одно правило с письмом.

**Ответ:** А — 72 часа, одноразовая.

### T3. Кто может быть найден по @username (если А или В в T1)

**Контекст.** Если бот хранит username всех пользователей, любой пациент может проверять, пользуется ли кто-то ботом («есть ли @ivanov в дневнике давления») — это утечка о здоровье.

- **А** — искать только среди **врачей**: врач регистрируется в боте явно (команда `/iamdoctor` или кнопка из приглашения), его username хранится в `doctors`; пациенты не ищутся никогда. Ответ «не найден» одинаков для «нет в боте» и «не врач».
- **Б** — хранить username всех пользователей бота и искать по всем.

**Моё мнение:** А.

**Ответ:** А — только врачи, одинаковый ответ «не найден». Критично для приватности: нельзя проверять, «болеет ли этот человек».

### T4. Как врач регистрируется в боте

- **А** — только через ссылку-приглашение от пациента (T1-Б): нажал «Старт» по ссылке → стал врачом этого пациента.
- **Б** — А + команда `/iamdoctor` (врач сам, без пациента): бот спрашивает ФИО (≤ 100) → врач зарегистрирован, его можно найти по @username.
- **В** — свой вариант.

**Моё мнение:** Б — иначе поиск по @username (T1-А) никого не найдёт до первого приглашения.

**Ответ:** Б — через ссылку + /iamdoctor: врач может зарегистрироваться сам, до приглашения пациента.

### T5. Онбординг пациента у врача

**Контекст.** Сейчас `/start` любого нового человека запускает онбординг пациента (часовой пояс, цели) и создаёт строку `users`.

- **А** — врач, пришедший по ссылке-приглашению или через `/iamdoctor`, онбординг пациента не проходит; у него отдельное короткое меню врача (см. T7). Если он позже сам нажмёт «Записать давление» или `/start` без параметра — обычный онбординг (врач может быть и пациентом).
- **Б** — врач проходит обычный онбординг, как все.

**Моё мнение:** А.

**Ответ:** А — врач не проходит онбординг пациента, видит меню врача.

### T6. Согласие врача

- **А** — по приглашению в Telegram бот показывает врачу «Пациент {имя} открыл вам доступ к дневнику давления» и кнопки «Принять» / «Отклонить»; «Принять» → `status='active'`, пациенту — уведомление «Врач {имя} принял приглашение».
- **Б** — доступ активируется сразу при нажатии «Старт» по ссылке (как сейчас — при открытии ссылки в кабинете).

**Моё мнение:** А — у врача должен быть выбор, а пациенту полезно знать, что приглашение принято.

**Ответ:** А — кнопки «Принять» / «Отклонить». Явное согласие правильно и юридически, и технически.

### T7. Что врач может делать в боте

Можно выбрать несколько.

- **1** — «Открыть кабинет врача»: бот присылает одноразовую ссылку входа в кабинет (15 минут) — вход без пароля и без участия пациента.
- **2** — «Мои пациенты»: список пациентов (только `active`) с кнопкой «Открыть в кабинете» по каждому.
- **3** — уведомление врачу, когда пациент нажал «Отправить отчет».
- **4** — уведомление врачу, когда пациент отозвал доступ.

**Моё мнение:** 1 + 2 + 3. 4 — по желанию: отзыв и так виден в кабинете (пациент исчезает из списка).

**Ответ:** 1 + 2 + 3 + 4 — «Открыть кабинет», «Мои пациенты», уведомление об отчёте, уведомление об отзыве доступа.

### T8. Хранение врача из Telegram в БД

**Контекст.** `doctors.email` сейчас NOT NULL UNIQUE — врач из Telegram может не иметь e-mail. Изменение схемы требует миграции живой БД (как `_migrate_medications` в `bot/db.py`).

- **А** — в `doctors` добавить `telegram_id` (INTEGER NULL UNIQUE) и `telegram_username` (TEXT NULL); `email` сделать NULL-able (UNIQUE сохраняется для непустых); CHECK — есть хотя бы одно из `email` / `telegram_id`. Миграция пересборкой таблицы при старте.
- **Б** — отдельная таблица `doctor_telegram` (doctor_id, telegram_id, username), `doctors` не трогать; врачу без e-mail — служебный адрес-заглушка.
- **В** — свой вариант.

**Моё мнение:** А — честная модель; заглушки e-mail в Б будут мешать и рассылке, и кабинету.

**Ответ:** А — telegram_id и telegram_username в doctors, email NULL-able, CHECK.

### T9. Один врач — два пути

**Контекст.** Один и тот же врач может быть добавлен одним пациентом по e-mail, другим — по Telegram. Получатся две записи `doctors`.

- **А** — пока не объединять; в кабинете врач видит пациентов той записи, через которую вошёл.
- **Б** — врач в боте может указать свой e-mail («Привязать e-mail»): если врач с таким e-mail уже есть — записи объединяются (связи переносятся), подтверждение — письмом со ссылкой.
- **В** — свой вариант.

**Моё мнение:** А сейчас; Б — отдельной задачей, когда появятся такие врачи.

**Ответ:** А — пока не объединять; врач видит пациентов той записи, через которую вошёл.

### T10. Обновление username

- **А** — username врача обновляется при каждом его сообщении боту (люди меняют username).
- **Б** — сохраняется один раз при регистрации.

**Моё мнение:** А.

**Ответ:** А — при каждом сообщении.

## Часть N. Новые развилки — найдены при подготовке правок SPEC

В SPEC-диффе стоят варианты «Моё мнение»; если выберете другое — поправлю дифф.

### N1. Одноразовость ссылки на 72 часа

**Контекст.** Сейчас использованные ссылки врача (`jti`) помнит только память процесса кабинета (`web/cabinet/doctor_auth.py`). При 15 минутах это терпимо; при 72 часах любой перезапуск кабинета (деплой) снова делает уже использованную ссылку рабочей.

- **А** — таблица `used_tokens` (jti PK, expires_at): кабинет списывает ссылку в БД, просроченные строки чистятся при старте.
- **Б** — оставить в памяти процесса.

**Моё мнение:** А.

**Ответ:** А — таблица used_tokens. При 72 часах перезапуск кабинета — плановый деплой, без персистентности перехваченная ссылка снова станет рабочей.

### N2. Код ссылки-приглашения в Telegram

**Контекст.** Параметр `?start=` у Telegram — до 64 символов `A-Z a-z 0-9 _ -`; подписанный токен `itsdangerous` туда не помещается.

- **А** — таблица `doctor_invites` (code — 22 случайных символа, user_id, created_at, expires_at, used_at); ссылка `https://t.me/<бот>?start=doc_<code>`. Одноразовость и 72 часа — по таблице.
- **Б** — короткий HMAC-токен без таблицы (user_id + срок + подпись), одноразовость — через N1.

**Моё мнение:** А — проще проверить, видно, сколько приглашений висит, и отзыв приглашения пациентом возможен.

**Ответ:** А — таблица doctor_invites: видно активные приглашения, их можно отозвать, админ видит происходящее; одноразовость проверяется без отдельной таблицы.
