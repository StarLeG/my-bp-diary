## 1. Что сейчас (факты для сверки)

### Шапка отчёта («Сводка»)

Один расчёт `bot/services/stats.py::summary` (`StatsSummary`) — и в ЛК
(`dashboard.html`, блок «Сводка за период»), и в PDF (`pdf_report.summary_lines`).
Строки сейчас (дословно, формат PDF):

```
Записей: 48
Систолическое: в среднем 147 (116–180)
Диастолическое: в среднем 90 (56–120)
Пульс: в среднем 62
Тренд: растёт
Цель: выше цели
Лекарства: принято 25 из 42 приёмов
```

То есть **диапазоны min–max уже есть** в скобках — но только числом, без даты и
времени, без указания записей-экстремумов. Поля `sys_min`/`sys_max`/`dia_min`/
`dia_max` в `StatsSummary` — просто числа (`min(systolic)` / `max(systolic)`),
момент записи-экстремума не сохраняется.

### График

- **ЛК**: три панели Chart.js (САД, ДАД, Пульс) — `partials/bp_charts.html`,
  под сводкой, после «Средних по дням»; легенда зон списком.
- **PDF**: графиков **нет** — SPEC §10.1 прямо: «графиков и дополнительных
  разделов (комментарии врача, журнал приёмов, список лекарств) в нём нет».
- **Бот**: только текстовая сводка (SPEC, «Стек»: графики и диаграммы в боте —
  только текстовая сводка).

### Лента дня (ЛК, `history_day.html` + `diary_feed.py`)

Три вида строк в одной таблице (`stacked-table`):

| Вид | Рендер | Кнопки действий |
|---|---|---|
| Измерение (`bp`) | полная строка колонок: Время, Сист., Диаст., Пульс, Лекарство, Самочувствие, Заметка | в колонке «Действия»: «✏️» (`btn btn-ghost`) + «🗑» (`btn-del`) |
| Событие (`event`) | `tr.feed-row.feed-event`: `td.feed-line` на все колонки, текст «13:20 — 📝 Заметка: …» | inline после текста (`td.feed-line .actions`): «✏️» + «🗑» |
| Приём (`intake`) | `tr.feed-row.feed-intake`: текст «13:20 — 💊 Приём лекарств: … — Принято ✓» | inline после текста; **журнал записи измерения (`is_journal_log`) кнопок не имеет** |

По скриншоту-находке видно: кнопки разных размеров («✏️» — крупная с рамкой,
«🗑» — мелкая), плавают после текста на разной высоте (у строк разной длины),
у строк приёмов кнопок нет вовсе, строки измерений подсвечены заливкой зон,
строки событий/приёмов — нет.

### PDF-таблица

`pdf_report.py` — таблица только по `measurements` (колонки Дата, Время, Сист.,
Диаст., Пульс, Лекарство, Самочувствие, Заметка), после неё — «Заключения врачей»
(только у пациента). Строки событий и standalone-приёмов в PDF **не попадают**
(ограничение SPEC §10.1, п. 27 — осознанное решение 0.6.2). Колонка «Заметка» —
это `m.note` самого измерения; заметки-события (`diary_events` типа `note`) —
отдельные строки ленты, их в PDF нет.

## 2. Находка 1 — шапка отчёта: макс/мин давление и график

### R1. Форма строки с максимальным и минимальным давлением

«Ещё запись с максимальным и минимальным давлением» — что именно показывать?

- **А** — две строки сводки с записями-экстремумами (дословный формат):
  «Максимальное: 180/120 (16.11.2026, 21:20)» и
  «Минимальное: 116/56 (12.11.2026, 07:30)» — с датой и временем;
- **Б** — одна строка: «Макс/мин: 180/120 (16.11, 21:20) — 116/56 (12.11, 07:30)»;
- **В** — своё (впишите формат дословно).

**Ответ:** **А** — две отдельные строки с датой и временем: «Максимальное: 180/100
(13.11.2026, 12:48)» и «Минимальное: 116/81 (15.11.2026, 12:54)» (примеры — по
данным образца PDF 0.7.1; в исходном вопросе стояла «смесь» 180/120 из разных
записей, исправлено по ревью). Строки читаются
проще, чем одна длинная, и в PDF они не переносятся. Год остаётся — период отчёта
может пересекать границу года.

### R2. Критерий «максимального» и «минимального» давления

Давление — пара (САД, ДАД). По чему выбирать запись-экстремум?

- **А** — по систолическому (максимум — запись с наибольшим САД, минимум — с
  наименьшим); при равенстве САД — по ДАД;
- **Б** — по обеим величинам независимо: 4 числа — макс/мин САД и макс/мин ДАД
  (могут быть из разных записей), с датами каждой;
- **В** — своё (например, по среднему АД (САД+ДАД)/2).

**Ответ:** **А** — выбор идёт по САД, при равенстве по ДАД. Для максимума при
равном САД берётся больший ДАД, для минимума — меньший. Если равны оба значения —
берётся более поздняя запись. Так экстремум остаётся реальной записью с одним
временем, а не смесью чисел из разных дней (как в варианте Б). Независимые min/max
САД и ДАД уже есть в скобках построчных диапазонов — не дублируем. В `StatsSummary`
вместе с числами хранится момент записи-экстремума.

### R3. График: какой и куда

«…а также график …» — в PDF сейчас графиков нет (SPEC §10.1 — ограничение,
для изменения нужно явное решение). В ЛК графики уже есть (САД, ДАД, Пульс).

- **А** — линейный график САД и ДАД по записям за период (по оси X — время),
  в PDF сразу после сводки, до легенды зон; пульс не показывать;
- **Б** — то же + пульс третьей линией (или отдельной панелью);
- **В** — столбчатый график средних по дням (как блок «Средние по дням» ЛК);
- **Г** — своё.

Уточнение: график рисуется в PDF средствами отрисовки (полноценный PNG из
Chart.js в серверном PDF недоступен — рисуем линиями fpdf2 или рендерим PNG
сервером). Предпочтение — **линейный график линиями fpdf2** (без новых
зависимостей), если не указано иное.

**Ответ:** **А** — линейный график САД и ДАД по времени, линиями fpdf2, сразу
после сводки и до легенды зон. Пульс — в другой области значений, перегружает
небольшой график; в ЛК он уже есть отдельной панелью. Если позже понадобится —
пульс можно добавить отдельной маленькой панелью. Новых зависимостей не нужно.

### R4. Область изменений сводки

Строки макс/мин (R1) — куда добавлять?

- **А** — везде, где сводка: ЛК «Сводка за период», PDF (бот, ЛК, врач) —
  одно и то же поле `StatsSummary`, единообразно;
- **Б** — только в PDF (шапка отчёта);
- **В** — PDF и ЛК пациента, но не у врача;
- **Г** — своё.

**Ответ:** **А** — везде: ЛК, PDF из бота, из ЛК и у врача. Источник один
(`StatsSummary`) — расхождений между ЛК и PDF не будет. Врачу эти строки нужнее
всего. В ЛК график уже есть, туда добавляются только две строки.

## 3. Находка 2 — лента дня: единообразие

### R5. Что именно «не красиво» (отметьте)

- **а)** кнопки действий разных размеров и стилей («✏️» крупная с рамкой vs
  «🗑» мелкая);
- **б)** кнопки у событий/приёмов «плавают» после текста на разной высоте
  (inline, у каждой строки своя позиция);
- **в)** у строк приёмов-журнала кнопок нет, у заметок — есть (разный состав);
- **г)** разная высота строк и отступы (измерения vs события vs приёмы);
- **д)** своё: …

**Ответ:** **а, б, в, г** — все четыре пункта подтверждены: кнопки разных
размеров; кнопки «плавают» после текста; у приёмов кнопок нет; строки измерений
подсвечены зонами, а события и приёмы — нет, и высота строк разная.

### R6. Вариант единообразия

- **А** — **единая колонка «Действия»**: и строки событий, и строки приёмов
  получают кнопки в ту же правую колонку, что и у измерений (текст — в колонке
  «Заметка» через `colspan`, кнопки — в «Действиях»). Кнопки одного размера и
  стиля везде.
- **Б** — **карточки**: строки событий/приёмов — карточки с кнопками в правом
  верхнем углу, одинаковой формы; измерения остаются таблицей.
- **В** — **нормализация inline**: кнопки остаются после текста, но одного
  размера (например, иконочные 32×32), с фиксированным отступом, без «плавания».
- **Г** — своё (опишите дословно).

**Ответ:** **А** — единая колонка «Действия» для всех типов строк. Текст события
или приёма занимает `colspan` до колонки «Заметка». Это решает пункты а, б и г
одновременно. Для журнала приёма, привязанного к измерению (`is_journal_log`),
нужна пустая ячейка в колонке «Действия» — строка остаётся выровненной, а
редактировать такой приём по-прежнему можно только через само измерение.

### R7. Вид кнопок действий

- **А** — оставить иконки «✏️» / «🗑», но одинакового размера (иконочные кнопки
  32×32, единые у всех типов строк);
- **Б** — текстовые кнопки «Изменить» / «Удалить» (по словарю §16.2
  «Единый UI-канон кнопок»);
- **В** — иконка + подпись («✏️ Изменить», «🗑 Удалить»);
- **Г** — своё.

**Ответ:** **А** — иконки «✏️» и «🗑» одного размера (32×32) у всех типов строк,
с `title` и `aria-label`. Измерения уже используют иконки — изменений меньше
всего; колонка остаётся узкой, мобильный stacked-table не раздувается. Оговорка
автора про канон §16.2 проверена: канон как раз требует иконки («✏️» — `btn-ghost`
в строке, «🗑» — красная без заливки, словарь — `title="Удалить"`), текстовые
подписи не нужны — вариант В не требуется.

## 4. Находка 3 — «в PDF этих данных нету»

### R8. Каких данных не хватает в PDF (уточнение)

На находке — таблица PDF (только измерения). «Этих данных» = ?

- **А** — данных ленты дня: событий дневника (заметки, питание, стресс, сон) и
  строк приёмов лекарств — того, что видно в ленте ЛК;
- **Б** — данных находки 1 (макс/мин давления и графика) — их в PDF нет;
- **В** — и того, и другого;
- **Г** — своё.

**Ответ:** **В** — и то, и другое. Формулировка находки двусмысленна, но находка 3
стоит сразу за находкой 1 и описывает общее впечатление от PDF. Безопаснее закрыть
оба пункта: макс/мин с графиком и данные ленты.

### R9. Если данные ленты (вариант А/В из R8) — как включать в PDF

Ограничение SPEC §10.1 («События дневника в PDF не включаются», п. 27) было
осознанным решением 0.6.2 — для изменения нужно явное решение автора.

- **А** — **строками в ту же таблицу** хронологически (как в ленте ЛК: «13:20 —
  Заметка: …», «13:20 — Приём лекарств: …»), в колонках Сист./Диаст./Пульс — «—»;
- **Б** — **отдельным разделом** «События дневника» после таблицы (как
  «Заключения врачей»: дата/время + тип + текст);
- **В** — **счётчиком в сводке** («События: N, приёмы: M») без деталей;
- **Г** — не включать (ограничение сохраняем).

**Ответ:** **Б** — отдельный раздел «События дневника» после таблицы, по аналогии
с «Заключениями врачей»: дата и время, тип, текст. Таблица измерений остаётся с
фиксированными колонками, без строк с прочерками в Сист./Диаст./Пульс. Раздел
хронологический — врач видит все заметки подряд. Приёмы, привязанные к измерению,
не дублируются (уже отражены в колонке «Лекарство») — попадают события и
standalone-приёмы. Вариант А точнее воспроизводит ленту ЛК, но заметно усложняет
вёрстку таблицы через `colspan`. Это меняет SPEC §10.1 и п. 27 — явное решение
автора получено (2026-11-17). Правки: формулировки §10.1 («графиков … в нём нет»,
«события в PDF не включаются»), тесты в §13, проверки F7–F9 в авто-приёмке.

## 5. Уточнения графика (§10.1, R3) — по ревью 2026-11-17

**Статус:** ответы на R10–R13 получены и утверждены (2026-11-17) — все **А**.

Ревью диффа SPEC: примеры экстремумов исправлены (180/100 и 116/81 — по данным
образца PDF 0.7.1), три устаревших «события в PDF не включаются» (§21, §6.14, §10)
сняты, порядок разделов приведён к одному (шапка → сводка → график → легенда →
таблица → «События дневника» → «Заключения врачей»), формулировка про журнал
приёмов уточнена (отдельного раздела нет, standalone-приёмы — в «Событиях
дневника»), содержимое раздела определено (строка «ДД.ММ.ГГГГ ЧЧ:ММ — тип —
текст», `summary` по словарю CSV событий, `note` полностью, лимит 5000 — по
измерениям, правило PDF без измерений вынесено в R14 — утверждено: А, PDF без
измерений не формируется). Осталось зафиксировать
детали графика:

### R10. Размер графика

Сводка занимает ~9 строк, график не должен сдвинуть таблицу на вторую страницу.

- **А** — фиксированная высота 50 мм на всю ширину полезной области (A4
  альбомная, поля 10 мм) — таблица гарантированно начинается на первой
  странице;
- **Б** — фиксированная высота 60 мм (крупнее, риск сдвига начала таблицы);
- **В** — своё значение.

**Ответ:** **А** — фиксированная высота 50 мм на всю ширину полезной области
(A4 альбомная 297 × 210, поля 10 мм → рабочая область 277 × 190 мм). Сводка ~45–50
мм + график 50 мм + легенда ~10 мм ≈ 105 мм — остаётся ~85 мм, таблица
гарантированно начинается на первой странице. Вариант Б (60 мм) повышает риск
переноса начала таблицы на вторую страницу. 50 мм достаточно для читаемого
линейного графика САД/ДАД с пороговыми линиями и подписями осей.

### R11. Крайние случаи (одна запись и до 5000 точек)

- **А** — одна запись: маркер без линии; до 30 точек: линия + маркеры; больше:
  линия без маркеров, при > 500 точек — прореживание с сохранением экстремумов
  (линия остаётся);
- **Б** — одна запись: маркер; много точек: только маркеры (без линии);
- **В** — одна запись: маркер; много точек: линия по всем точкам без прореживания
  (fpf2 отрисует 5000 сегментов, файл крупнее);
- **Г** — своё.

**Ответ:** **А** — одна запись: маркер без линии; до 30 точек: линия + маркеры;
больше 30: линия без маркеров (маркеры «сливаются»); при > 500 точек — прореживание
с сохранением экстремумов (минимумов и максимумов САД/ДАД), линия остаётся.
Иначе экспорт за всё время (до 5000 точек) даст крупный файл и визуально плотный
график без выигрыша в читаемости (В — отклонён). График — иллюстративный, не для
точных измерений.

### R12. Ось X

- **А** — по реальному времени: видны пропуски между днями (ночные интервалы,
  пропущенные дни) — соответствует смыслу «график по записям за период»;
- **Б** — по порядку записей (эквивалентное расстояние между соседними) — все
  точки видны, но пропуски времени невидимы;
- **В** — своё.

**Ответ:** **А** — по реальному времени: видны пропуски между днями (ночные
интервалы, пропущенные дни) — клинически значимо для врача и соответствует смыслу
«график по записям за период» (§10.1: «по времени»). Вариант Б (по порядку
записей) искажает восприятие времени: записи с разницей в минуту и в неделю
выглядят равноудалёнными.

### R13. Пороги на графике

- **А** — линии 140 (САД) и 90 (ДАД) тонким пунктиром — единообразие с зонами
  ЛК, сразу видно превышение; подписи «140» / «90» у оси Y;
- **Б** — без порогов, только ряды САД/ДАД (минимализм);
- **В** — своё.

**Ответ:** **А** — линии 140 (САД) и 90 (ДАД) тонким пунктиром, подписи «140» /
«90» у оси Y. Единообразие с зонами ЛК (`web/cabinet/chart_zones.py`); верхних
порогов достаточно — они отмечают клинически значимые уровни; пунктир не
перегружает график. Вариант Б (минимализм) менее информативен: график дополняет
сводку, а не заменяет её.

### R14. PDF без измерений, но с событиями (по ревью 2026-11-17)

Формулировка «события без измерений PDF не порождают» двусмысленна. Правило
нужно одно для всех точек (бот, ЛК, врач):

- **А** — **PDF строится только при наличии измерений**: за период нет записей
  давления — файл не формируется («За этот период записей нет»), даже если
  события есть. Прежнее правило §10.1 сохраняется без изменений; события —
  дополнение к отчёту по давлению, а не самостоятельный документ.
- **Б** — **PDF строится и при одних событиях**: таблица измерений пуста
  (или без неё), раздел «События дневника» есть. Новое поведение: меняется
  правило пустого периода для всех трёх точек экспорта и для проверки
  «пустой период» в тестах.

**Ответ:** **А** — PDF строится только при наличии измерений. Минимальное
изменение: прежнее правило §10.1 сохраняется, R9-Б добавляет раздел к
существующему отчёту, а не превращает PDF в самостоятельный дневник событий.
Смысл документа — отчёт по давлению: без измерений он теряет основной предмет,
а события — контекст вокруг измерений (§4.18: «события их не дублируют и не
заменяют»). Согласовано с R9-Б («таблица измерений остаётся с фиксированными
колонками» — таблица предполагается). Обратная совместимость: «За этот период
записей нет» сохраняется во всех трёх точках экспорта. PDF-дневник событий без
давления, если понадобится, — отдельная функция, а не изменение правила пустого
периода. Тесты «пустой период» остаются прежними (уточняющая фраза в §10.1 — не
изменение правила).
