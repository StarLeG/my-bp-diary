# Отметка о посещении и заключение врача: вопросы

Продолжение «Визитов и анализов» (§6.13, 0.5.8; вопросы — `doc/APPOINTMENTS-QUESTIONS.md`, В1–В24, Н1–Н8). Две доработки:

1. **Отметка о посещении из карточки.** Сейчас в карточке события нельзя отметить, что визит состоялся: в день события там только «📄 Отчёт для врача» / «✏️ Изменить» / «Отменить» / «🗑 Удалить», кнопки «✓ Был(а)» появляются лишь на 1–3-й день после (и пропадают совсем после 3 дней).
2. **Заключение врача.** Пользователь сам вручную заполняет текст заключения — бот хранит его вместе с записью о посещении. **Распознавания фото нет** (ваше решение 13.11.2026, см. ниже).

Сверено с кодом (0.5.10):
- `bot/keyboards.py` `ap_card_kb`: `upcoming` (`planned` и `starts_on >= сегодня`, **день события включительно** — `is_upcoming`) — «📄 Отчёт для врача» (у `doctor`), «✏️ Изменить», «Отменить визит»/«Отменить», «🗑 Удалить», «Назад»; `waiting` (`planned`, 1–3 дня после даты — `status_key`) — «✓ Был(а)»/«Перенёс(ла)»/«Не был(а)» (`ap:after:{id}:{done|moved|missed}`) + «🗑 Удалить», «Назад»; `unmarked` (позже 3 дней) — только «🗑 Удалить», «Назад».
- `bot/services/appointments.py`: `awaiting_answer` — `planned`, дата наступила, ≤ 3 дней (`APPOINTMENT_STATUS_TIMEOUT`); `set_status` — идемпотентный `UPDATE … WHERE status='planned'`, флаги `sent_*` не трогает. Тик (§6.13) шлёт уведомления только `planned`-строкам — значит ранняя отметка уже гасит «Как прошёл визит?» без дополнительных правок.
- Уведомление «Как прошёл визит?» (20:00 в день события / 10:00 следующего) — единственная кнопка отметки сейчас; в карточке её нет ни в день события, ни позже 3 дней.
- Кнопки «Записать следующий?» (`ap:next:{id}:{n}`), перенос после события (Н1: `moved` + новая `planned`), PDF «Отчёт для врача» (`ap:report:{id}`, §10.1) — как есть, не меняются. PDF-генератор **один на три места** (§10.1: бот, ЛК и кабинет врача) — важно для У2.
- Свободный ввод в боте — FSM, как «Другой…» и заметка (§6.13, допущение 4); ограничение длины — «Слишком длинно — до N символов. Напишите короче.» (тексты §11).
- Согласие: `CONSENT_VERSION` / `POLICY_DATE` — `bot/services/consent.py` (сейчас `"2026-11-11"`); политика — `web/landing/privacy.html`.
- Схема: `SCHEMA_VERSION` (`bot/db.py`, `PRAGMA user_version`) сейчас 9; поколение 9 — `users.ui_large` (0.5.10), поколение 8 — `appointments` (0.5.8).
- `bot/services/backup.py` охватывает только файл SQLite (шифрованный архив); файлы на диске в бэкап не попадают — важно для варианта с хранением фото (В30-В).

**Решено (вы, 13.11.2026):** без распознавания текста. Фото в текст не превращается; текст заключения пользователь пишет сам. Варианты OCR (Tesseract / облачный OCR / LLM-vision) и передача фото третьим сторонам сняты из обсуждения.

**Как отвечать:** букву варианта (или свой) — в строку «Ответ». «Моё мнение» — только мнение. Код не пишу до ответов, правки SPEC и её утверждения. Нумерация — продолжение В1–В24: здесь В25–В38 и уточнения У1–У3.

## Часть 1. Отметка о посещении

### В25. Кнопки отметки в карточке

Карточка события в день события и после. Три возможных вида (раскладка — UI-канон 0.5.10: пары §11, крупный режим по одной кнопке в строке):

- **А** — одна кнопка «✓ Был(а)» (у `lab` — «✓ Сдал(а)»), callback — существующий `ap:after:{id}:done`. Дальше — как после уведомления: «Отметил ✓» + «Записать следующий?» (В11). «Не был(а)» и перенос — прежними путями («✏️ Изменить», «Отменить»).
- **Б** — три кнопки «✓ Был(а)» / «Перенёс(ла)» / «Не был(а)» прямо в карточке (`ap_after_kb`, те же `ap:after:{id}:{done|moved|missed}`) — как уже сделано в карточке `waiting` (1–3 дня после). Всё по текущим сценариям: `done` → «Записать следующий?»; `moved` → Н1 (прежняя строка `moved`, новая `planned`); `missed` → «Понятно, отметил.»
- **В** — одна кнопка «✓ Отметить» → экран «Как прошёл визит?» (тексты §6.13, три кнопки + «Назад» в карточку). Карточка не разрастается, но до отметки — лишнее нажатие.

**Моё мнение:** Б. Единообразно с `waiting`-карточкой и уведомлением, один код (`ap:after`), «Записать следующий?» работает без правок. Карточка в день события и так уже несёт 5–6 кнопок; три статусные — не перегруз. Кнопки видны **с дня события** (включительно): раньше исхода нет, а «✏️ Изменить» / «Отменить» для планов уже есть.

**Ответ:** Б — три кнопки «✓ Был(а)» / «Перенёс(ла)» / «Не был(а)» прямо в карточке, видны с дня события включительно. Подписи по типу явно (поправка по ревью 13.11.2026, п. 1): `doctor`, `exam` — «✓ Был(а)» / «Перенёс(ла)» / «Не был(а)»; `lab` — «✓ Сдал(а)» / «Перенёс(ла)» / «Не сдал(а)» (все три кнопки). Callbacks и окно уведомления — У1.

### В26. Окно отметки из карточки

Сейчас `waiting` — только 1–3 дня после даты (Н2), позже в карточке — лишь «Удалить».

- **А** — без ограничения: любой `planned` с дня события можно отметить из карточки, даже «без отметки» (позже 3 дней). Кнопки самого уведомления по-прежнему живут 3 дня («Это сообщение устарело»).
- **Б** — ≤ 3 дней, как сейчас у `waiting`; позже — только «Удалить».
- **В** — ≤ 7 дней.

**Моё мнение:** А. Карточка — не устаревшее сообщение: человек может вспомнить о визите через две недели и зафиксировать историю («когда последний раз был у кардиолога» — польза В13). Н2 остаётся верной для кнопок уведомления.

**Ответ:** А — окно отметки из карточки не ограничиваем: любой `planned` с дня события, включая «без отметки». Уведомление «Как прошёл визит?» по-прежнему живёт 3 дня (как реализовать разные окна на одном callback — У1).

## Часть 2. Заключение врача: ручной ввод

### В27. Для каких событий нужно «заключение»

- **А** — только `doctor`: кнопка «📝 Заключение врача».
- **Б** — все типы, с разными названиями: `doctor` — «📝 Заключение врача», `lab` — «📝 Результаты анализов», `exam` — «📝 Протокол обследования».
- **В** — все типы, одно название «📝 Заключение».

**Моё мнение:** Б. У обследования и анализов тоже есть результаты на руках (протокол ЭКГ, цифры из бланка), механика та же — только подпись другая.

**Ответ:** Б — все типы, с подписями: `doctor` — «📝 Заключение врача», `lab` — «📝 Результаты анализов», `exam` — «📝 Протокол обследования».

### В28. Фото заключения: оставлять ли

Распознавания нет, но фото может остаться как архив оригинала (фото бланка + набранный текст). Без фото сценарий — чисто текстовый.

- **А** — только текст: фото не принимаем, ничего не храним.
- **Б** — текст + необязательное фото: после ввода текста — «Прикрепить фото заключения?» («📎 Прикрепить» / «Без фото»); фото по кнопке «📎 Фото» присылается в чат из карточки (Telegram `file_id`, на сервере не хранится — см. В30).
- **В** — только фото, без текста — снимает вашу задачу «заполнить заключение», не рассматриваю.

**Моё мнение:** Б. Вы исходно хотели «сфотографировать и отправить» — без распознавания фото сохраняет ценность: оригинал бланка под рукой, а текст набран. Но если хотите максимум простоты — А, это честный минимум.

**Ответ:** Б — текст + необязательное фото. Фото — только Telegram `file_id`: файл на сервере не хранится, в ЛК и PDF фото не попадает.

### В29. Как вводится текст

FSM-ввод одним сообщением (как заметка и «Другой…», §6.13).

- **А** — без подтверждения: «Напишите текст заключения одним сообщением (до 4000 символов).» → сразу «Сохранил ✓» + текст; тут же кнопки «✏️ Исправить» (FSM, замена текста) / «🗑 Удалить» (если В31-Б) или возврат к списку (если В31-А). Длиннее 4000 — «Слишком длинно — до 4000 символов. Напишите короче.»; пустое — повтор приглашения.
- **Б** — с подтверждением: после ввода — «Так верно?» с текстом — «✅ Верно» / «✏️ Исправить» / «Отмена»; сохранение только после «Верно».

**Моё мнение:** А. Сохранённый текст тут же виден на экране, «✏️ Исправить» — рядом; подтверждение — лишний тап без новой информации.

**Ответ:** А — без подтверждения: ввод одним сообщением → «Сохранил ✓» + текст, рядом «✏️ Исправить» / «🗑 Удалить» или возврат к списку.

### В30. Схема хранения

- **А** — новая таблица `appointment_conclusions` (схема — поколение 9): `id` PK, `appointment_id` INTEGER NOT NULL FK `appointments.id` CASCADE, `text` TEXT NOT NULL `''` ≤ 4000, `photo_file_id` TEXT NULL (только при В28-Б), `created_at` DATETIME NOT NULL UTC + индекс `(appointment_id)`. Несколько записей на событие — лимит по В36. В ЛК — текст (фото по `file_id` вебу недоступно, см. В33).
- **Б** — одно заключение на событие: поля `conclusion_text` TEXT и `conclusion_photo_file_id` TEXT NULL прямо в `appointments` (миграция `ALTER TABLE`) — проще, но вторая страница/второй документ некуда.
- **В** — А + скачиваем фото в `data/appointment_docs/…` (поле `photo_path`): фото видно и в ЛК. Минус: медфото на диске, и `bot/services/backup.py` сейчас архивирует только SQLite — бэкап надо расширять (§20).

**Моё мнение:** А. Даже «одно заключение» завтра захочет вторую страницу; поля в `appointments` — тупиковый путь. Фото — только `file_id` (В30-В — отдельной задачей, если фото понадобится в ЛК).

**Ответ:** А — таблица `appointment_conclusions` (`id`, `appointment_id` FK CASCADE, `text` ≤ 4000, `photo_file_id` NULL, `created_at`, индекс `(appointment_id)`); поля в `appointments` не добавляем. **Поправка: схема — поколение 10, не 9** (поколение 9 занято `users.ui_large` в 0.5.10). Поправка по ревью (п. 5): `text` — `NOT NULL` **без** `''` — пустой текст отклоняется сервисом; фото существует только вместе с текстом.

### В31. Экран заключений: просмотр, правка, удаление

- **А** — полноценный экран: в карточке строка «📝 Заключение: «первые 60 символов…»» (несколько — «📝 Заключений: N») и кнопка «📝 Заключение» → список записей («1. «Рекомендовано продолжить…»»), у каждой — «✏️ Текст» (FSM), «📎 Фото» (прислать/заменить, если В28-Б), «🗑 Удалить» (с подтверждением); «➕ Добавить», «Назад».
- **Б** — максимум одно заключение: текст прямо в карточке события, кнопки «✏️ Заключение» (добавить/исправить), «🗑 Удалить» (с подтверждением).

**Моё мнение:** А — заключения на две страницы и «заключение + протокол» — обычное дело; Б упрётся в них сразу. Удаление — с подтверждением, как «Удалить» события (§6.13).

**Ответ:** А — полноценный экран заключений: строка-превью и кнопка «📝 Заключение» в карточке → список записей; у каждой «✏️ Текст», «📎 Фото» (при В28-Б), «🗑 Удалить» с подтверждением; «➕ Добавить», «Назад».

### В32. Что такое «отчёт о посещении врача» — куда прикрепляется текст

Вы написали: «распознает фото и сохраняет его в текст и прикрепляет к отчету о посещении врача». Уточните, что для вас «отчёт о посещении» (распознавания больше нет, но вопрос «куда прикреплять» остаётся):

- **А** — сама запись о событии (карточка в боте + раздел ЛК): текст заключения — её часть, ничего нового не генерируем.
- **Б** — новый документ «Итоги визита» (PDF: вид, название, дата, заметка, заключение) — кнопка в карточке «📄 Итоги визита».
- **В** — раздел «Заключения врачей» в существующем PDF «Отчёт для врача» (§10.1, `bot/services/pdf_report.py`): к следующему визиту выгружается и давление, и прошлые заключения.
- **Г** — А + В.

**Моё мнение:** Г. Прикрепить к записи — минимум, который вы описали; добавить заключения в PDF-отчёт — дёшево (генератор уже есть) и полезно: пришёл к врачу — показал и давление, и прошлые заключения. Б — отдельный документ, если попросят.

**Ответ:** Г — А + В: заключение — часть записи о событии (карточка в боте и раздел ЛК), и раздел «Заключения врачей» в PDF «Отчёт для врача». Отдельный PDF «Итоги визита» не делаем. Оговорка: PDF-генератор общий с кабинетом врача — см. У2. Состав раздела (п. 3 ревью): по строке на заключение — «{иконка} {title} — {ДД.ММ.ГГГГ}» и текст следующим абзацем; сортировка по дате события; фото и заметка события не включаются; раздел — только если за период отчёта есть заключения.

**Моё мнение:** А. Текст — главная ценность, он доступен и с компьютера; фото — в боте по кнопке.

**Ответ:** А — в ЛК текст заключений: просмотр, правка, удаление. Фото — только в боте по `file_id`, вебу оно недоступно. Добавление из ЛК — см. У3. Размещение в ЛК (п. 2 ревью): строка-превью в карточке события («📝 Заключение: «первые 60 символов…»» / «📝 Заключений: N») + раскрывающийся блок `<details>` со списком записей (текст каждой, «✏️ Изменить», «🗑 Удалить…»; внизу — «➕ Добавить») — как раскрывается форма правки события в 0.5.9.

### В35. Согласие и политика конфиденциальности
