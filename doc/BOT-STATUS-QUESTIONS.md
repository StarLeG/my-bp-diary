# Информация о недоступности бота: вопросы по деталям

Задача (2026-11-17): «добавить информацию для пользователя, если бот недоступен
(например, завис сервер) — и в бота, и в робота, с проверкой этого роботом».
Никакого кода бот-части до ответов и полного утверждения.

**Статус:** ответы на ST1–ST3 получены и утверждены (2026-11-17) — зафиксированы
ниже. Робот-часть сделана: `qa/test_menu_acceptance_e2e.py::TestBotAlive` —
первая проверка каждого прогона — бот отвечает за 20 с; тишина = вердикт
«❌ Бот недоступен (завис сервер или бот остановлен)», отчёт админу уходит
штатно (§22). Код бот-части — в релизе 0.7.0 (SPEC §12, §6.7, §16.1, §22).

**Как отвечать:** букву варианта (или свой) — в строку «Ответ». «Моё мнение» —
только мнение.

---

## 0. Техническая рамка (важно для выбора)

- **Бот мёртв (завис весь сервер, остановлен процесс)** — сам ничего сказать не
  может: он не отвечает. Информировать может только **внешняя** поверхность:
  QA-робот (уже умеет), аптайм-монитор, или страница/канал **вне** этого сервера.
  Статус-страница на том же сервере ляжет вместе с ботом — при «завис сервер»
  она бесполезна, но полезна при «упал только бот» (процесс умер, nginx жив).
- **Бот жив, но деградировал** (БД недоступна, системный сбой обработки) — может
  отвечать прямо в чате; это случай «информация в боте» (ST1).
- Проверка роботом («а в робота проверку этого») — уже есть: TestBotAlive +
  преждевременный SKIP «flood-лимит» с ясным текстом вместо таймаутов.

## 1. Вопросы

### ST1. Сообщение в чате при живом, но сбойном боте

Сейчас §12: любой неожиданный сбой хендлера → «Что-то пошло не так, попробуйте
ещё раз» (без деталей). Отличить «временный сбой бота» от «случайной ошибки»
можно: системные исключения (БД недоступна, «database is locked» после ретраев)
— это «бот недоступен».

- **А** — два уровня ответов: системные сбои (БД/инфраструктура) → «⚙️ Бот
  временно недоступен — идёт восстановление. Ваши данные в безопасности,
  попробуйте через несколько минут.» (дословно — утвердите в ответе); прочие
  ошибки — как сейчас «Что-то пошло не так…».
- **Б** — оставить одно «Что-то пошло не так, попробуйте ещё раз» на все случаи.
- **В** — своё.

**Моё мнение:** А — пожилой пользователь должен отличать «моя ошибка» от
«бот заболел»; фраза про «данные в безопасности» снимает тревогу.

**Ответ:** **А** — два уровня ответов; текст утверждён дословно: «⚙️ Бот
временно недоступен — идёт восстановление. Ваши данные в безопасности,
попробуйте через несколько минут.» (0.7.0)

### ST2. Статус на внешней поверхности (бот мёртв / упал только бот)

- **А** — строка «Статус бота» на лендинге: бот раз в минуту (тик уже есть,
  §6.7) пишет файл-хартбит `data/status.json` (`{"ok": true, "at": …}`), nginx
  лендинга отдаёт его статикой; JS на лендинге: «🟢 Бот работает» или
  «🔴 Бот не отвечает с HH:MM». Покрывает «упал только бот» (nginx жив); при
  «завис весь сервер» лендинг тоже лежит — это зона внешнего мониторинга (ST3).
- **Б** — статус-эндпоинт кабинета `GET /status` (читает тот же хартбит) +
  ссылка с лендинга и из «О боте».
- **В** — без статус-страницы: только оповещение из ST3 и пост в сообществе
  вручную.
- **Г** — своё.

**Моё мнение:** А — минимально (файл + тик + маленький JS), работает при
«упал бот», не тянет ни БД, ни кабинет; Б — вторым шагом, если захотите
«здоровье» в кабинете.

**Ответ:** **А** — `status.json` + JS на лендинге (легковесно, без БД и
кабинета). Уточнения автора (приняты): запись хартбита — в `try-except`
(не должна ронять бота); время в `status.json` — UTC, JS переводит в локальное
время браузера для «🔴 Бот не отвечает с HH:MM»; файл лежит в статической
директории лендинга (общий том с ботом, без маршрутизации). (0.7.0)

### ST3. Кто оповещает при полной недоступности («завис сервер»)

- **А** — QA-робот (внешний наблюдатель): при недоступности бота отчёт админу
  в Telegram «❌ Бот недоступен (не отвечает) — проверьте сервер» (база
  TestBotAlive уже готова; нужен регулярный запуск — cron на машине разработчика
  или расписание вручную).
- **Б** — внешний аптайм-мониторинг (вне этой задачи; например, UptimeRobot на
  статус-страницу ST2).
- **В** — оба.

**Моё мнение:** В — робот уже почти готов и шлёт отчёты; бесплатный внешний
монитор дешёвая страховка «завис весь сервер».

**Ответ:** **В** — QA-робот + внешний монитор. Уточнения автора (приняты):
запуск робота по cron раз в 15–30 минут (машина разработчика; если бот завис
ночью — узнаем до утра); внешний монитор (UptimeRobot) — на `/status.json`
лендинга, уведомления в Telegram. Настройка cron и монитора — вручную автором;
в репозиторий добавлены строки-образцы (§22). (0.7.0)
